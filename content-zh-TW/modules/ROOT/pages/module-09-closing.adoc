= 總結

在這場實作工作坊中，您完成了一段從共用 AI 基礎設施到受控 Edge 部署的企業級修復之旅。

您扮演了兩種常見的工作角色：

* 作為 **SRE 或 DevOps 從業者**，您打下了平台基礎：模型即服務、OpenShift AI、Llama Stack、MCP 伺服器、Grafana 可觀測性，以及對 RHEL 或 Edge 系統資料的受控存取。
* 作為**開發者**，您在 OpenShift Dev Spaces 中使用 AI 開發代理來生成程式碼、審查建議的變更、測試行為、分析遠端日誌，並準備修復工作流程。

最重要的收穫不是 AI 能夠生成文字或程式碼——而是 **AI 能夠在清晰的控制邊界內參與企業工作流程**，這個模式才是核心所在。

== 您建構並驗證了什麼

工作坊結束時，您練習了如何：

* 使用共用模型端點，而非為每個團隊或應用程式重複部署模型。
* 將 Playground 和開發工具連接到受治理的 MaaS 端點。
* 使用 MCP 伺服器向 AI 客戶端公開已核准的運維脈絡。
* 透過自然語言檢視 OpenShift 資源和應用程式日誌。
* 透過 Grafana 儀表板觀察模型使用量和平台活動。
* 在 OpenShift Dev Spaces 中為 Cline 設定私有模型端點。
* 在接受應用程式程式碼變更前先生成並審查。
* 使用測試和明確的預期結果驗證行為。
* 透過 Git、AAP 工作歷史和驗證輸出保持修復的可稽核性。

== 企業級模式

您完成的工作流程可以總結如下：

[cols="1,2"]
|===
|階段 |控制點

|模型存取
|RHOAI 公開共用、受治理的 MaaS 端點。

|脈絡存取
|MCP 伺服器提供對已核准工具和資料的範圍存取。

|調查
|AI 協助分析，但學員負責審查證據和建議的下一步。

|程式碼變更
|Cline 在開發者工作區提出原始碼變更，供人工審查。

|部署
|Git 和 AAP 提供受控的部署、驗證和稽核歷史。

|驗證
|修復後的應用程式以具體的通過/失敗行為進行測試。
|===

此模式刻意設計為模組化。在實際環境中，您可以將範例 portal 應用程式替換為其他工作負載、將 MCP 允許清單擴展到已核准的運維資料，或透過您現有的 GitOps 和自動化流程進行部署。

== 討論題目

使用以下問題，將本實驗與您自己的組織情境連結：

* AI 客戶端應被允許讀取哪些運維資料？哪些資料應保持不可存取？
* 哪些操作在 AI 輔助工作流程繼續執行前，應要求人工核准？
* 稽核證據應儲存在哪裡：Git、AAP 工作歷史、聊天記錄、工單系統，還是以上全部？
* 您會如何區分唯讀調查工具與部署或修復工具？
* 將 AI 生成的變更提升到生產環境前，需要哪些測試或驗證關卡？
