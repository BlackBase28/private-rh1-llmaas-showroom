[#event-driven-ai-remediation]
= 以 Agentic AI 實現事件驅動的受控修復

應用程式本身運作正常，但授權機制已損壞：一般使用者可以存取 `/admin`。

== 實驗目標

您將完成一個企業級的 AI 輔助修復流程：

* 使用 Red Hat OpenShift AI 和 MCP 工具調查事件
* 使用 OpenShift Dev Spaces 中的 Cline 修復應用程式程式碼
* 在部署前審查生成的程式碼差異
* 觸發已核准的 Ansible Automation Platform 修復工作
* 驗證一般使用者被拒絕存取，管理員可正常存取

== 確認損壞狀態

開啟您的 portal 路由：

[source,console,role=execute,subs=attributes+]
----

----

確認健康狀態端點正常運作：

image::en@modules:ROOT:event_stream_url.png[確認 Event Stream URL,width=80%]

接著進行事件接收測試：

. 切換至 Kernel CVE Radar 網站。
. 確認右上角顯示目前以 user1 身分登入。

image::en@modules:ROOT:cve-radar-header.png[確認 Kernel CVE Radar 登入身分,width=80%]

登入後，點選網站上的「Admin 資訊」進入管理頁面。

在尚未修復的版本中，一般使用者可以成功看到管理頁面的內容。這是本實驗刻意保留的 Broken Access Control 弱點。

返回 AAP 的 Event Stream 頁面，確認 Events received 次數增加，表示 Event Stream 已成功接收到 Event Forwarder 傳送的事件。

image::en@modules:ROOT:event_stream_count.png[確認 Events received 次數增加,width=80%]

== 6. 確認 Rulebook Activation

*所屬階段：階段 2｜事件監控與 EDA 準備*

從左側導覽列選擇：

*Automation Decisions → Rulebook Activations*

開啟屬於您個人 Organization 的 CVE Radar Activation：

[source,text,subs=attributes+]
----
{user} - CVE Radar Security Event Activation
----

確認 Activation 狀態為待處理。

image::en@modules:ROOT:rulebook_status.png[Rulebook Activation 待處理狀態,width=80%]

點選進入後，可以在下方看到 variables 設定。

image::en@modules:ROOT:rulebook_detail.png[Rulebook Activation 詳細設定,width=80%]

這些變數定義不同事件條件所對應的 Job Template 或 Workflow，名稱必須與既有資源一致。為確保 Lab 正常運作，請勿修改此處設定。

完成檢視 Rulebook「CVE Radar Security Event Activation」後，開啟右上方的 Activation 開關，並等待狀態變更為 Running。

Activation 便會接收 Event Stream 傳入的事件，並根據 Rulebook 決定要啟動 AI Analysis 或後續 Workflow。

image::en@modules:ROOT:rulebook_running.png[Rulebook Activation Running 狀態,width=80%]

== 7. 建立 AI Model Credential（實作設定 1）

*所屬階段：階段 3｜AI 分析準備*

CVE Radar - AI Risk Analysis Template 需要與 AI Model 溝通，因此必須建立連線使用的 Credential。請準備在 Module 05 取得的 AI Model URL 與 Token；本次 TAM Day Lab 提供的兩個 Model 均可使用。

=== 從命令列驗證 Model URL 與 Token

返回本說明右側的終端機操作，輸入以下內容。請將 <MODEL URL>、<TOKEN> 與 <MODEL_NAME> 替換為 Module 05 取得的實際資訊。

[source,bash]
----
curl -k https://portal-{user}.{openshift_cluster_ingress_domain}/healthz
----

[NOTE]
====
MODEL_URL 必須包含 /v1/chat/completions。
MODEL_NAME 則根據選擇 Model，設定為 "qwen3-4b-instruct" 或 "qwen3-30b-a3b-instruct-2507-fp8"。
====

執行以下測試：

[source,console,role=execute,subs=attributes+]
----
curl -k -c cookies.txt \
  -H "Content-Type: application/json" \
  -d '{"username":"user","password":"user123"}' \
  https://portal-{user}.{openshift_cluster_ingress_domain}/login
----

存取管理員頁面：

[source,console,role=execute,subs=attributes+]
----
curl -k -b cookies.txt -i \
  https://portal-{user}.{openshift_cluster_ingress_domain}/admin
----

----

== 使用 RHOAI Playground 調查

啟用以下 MCP 伺服器：

* Kubernetes MCP Server
* Rocket.Chat MCP Server

== 15. 核准修復 Workflow

*所屬階段：階段 5｜事件分析與核准*

從左側導覽列選擇：

*Automation Execution → Jobs*

開啟最新的 Workflow Job。

發通知訊息時，Workflow 也會先同步將網站切換至維護頁面，避免修復期間繼續提供有弱點的管理功能。接著 Workflow 會停在 Approval 節點，等待人工核准。

從左側導覽列選擇

*Automation Execution → Administration → Workflow Approvals*

開啟最新的 `Approve repaired web deployment`

image::en@modules:ROOT:workflow_approval.png[Workflow Approval,width=80%]

確認資訊正確後，選擇右上角的 *Approve*。

[IMPORTANT]
====
人工核准是本實驗的治理控制點。
AI 可以分析、規劃並提出修復建議，但在實際變更正式服務前，仍需由具備權限的人員核准。
====

== 治理討論

本實驗刻意保持明確的控制邊界：

* RHOAI 和 MCP 協助調查。
* Cline 在開發者工作區提出並套用原始碼變更。
* Git 記錄程式碼變更。
* AAP 執行部署和驗證。
* 修復前需要人工核准。
* AAP 工作歷史和聊天通知提供稽核脈絡。

此模式可透過將每位使用者的 OpenShift 工作負載替換為 AAP 清單、憑證和主機層級部署任務，擴展到 RHEL VM 目標。
